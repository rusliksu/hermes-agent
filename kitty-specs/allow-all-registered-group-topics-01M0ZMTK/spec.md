## Требуемое поведение

Регистрация Telegram-группы является разрешением для всех её forum topics. Уже существующие и созданные позднее топики не требуют ручного добавления в access registry. Каждый топик при этом остаётся отдельной conversation lane/session по `thread_id`.

Точное topic binding, если оно настроено, продолжает переопределять групповой default profile/scope. Для топика без точного binding используется безопасный shared-room default зарегистрированной группы.

## Приёмочные сценарии

1. Зарегистрированный участник пишет в новый топик зарегистрированной группы и проходит ingress до модели; новый `thread_id` не вызывает `missing_shared_scope_binding`.
2. Два разных топика одной группы получают разные session/memory namespaces и не смешивают историю.
3. Существующее точное topic binding сохраняет свой profile/scope и имеет приоритет над групповым default.
4. Незарегистрированная группа, неучастник, disabled group binding и malformed transport identity по-прежнему отклоняются до модели.
5. После staging rollout два сообщения Юли из показанного топика проходят access resolution; ответ доставляется в тот же chat/topic.

## Ограничения

- Не расширять owner/admin права, capabilities или private profiles.
- Не выводить доступ из названия группы, топика, username или display name.
- Не читать и не изменять tokens, credentials, auth/session files или `.env`.
- Изменения ограничены HOSTKEY staging; prod/старый live-контур не затрагивается.
- Restart и Telegram canary выполняются только после явного одобрения этого плана.

## Вне scope

- Автоматическое создание новых профилей по названию топика.
- Изменение mention/reply policy и логики выбора момента ответа в группе.
- Миграция других платформ или незарегистрированных Telegram-групп.
